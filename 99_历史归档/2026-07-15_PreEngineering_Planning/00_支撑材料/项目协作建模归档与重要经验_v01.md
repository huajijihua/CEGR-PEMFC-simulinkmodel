# 项目协作建模归档与重要经验_v01

本文档归档本轮 PEMFC-cEGR 项目中 Codex 与 Claude Code 协作建模、互相审查和纠偏过程中形成的重要经验。目标是沉淀可复用的协作规则、技术边界和高价值做法，不记录所有过程细节。

## 1. 本轮任务范围与结果摘要

本轮围绕 `02_多物理场机理模型演示` 下的 COMSOL 二维燃料电池模型展开，三个 Server 并行工作：

| Server | 角色 | 模型 |
|--------|------|------|
| 2036 | 参考源 | `20260624-结构简化燃料电池-阴极尾气循环.mph` |
| 2037 | Claude Code 工作区 | `20260629-空.mph` → 插入了 comp1 + 全部 func |
| 2038 | Codex 工作区 | `20260629-空2.mph` → 插入了 comp1 + 全部 func |

主要工作：

- 排查 COMSOL 模型编译错误的根因（外部 CSV 依赖 + 列结构错误）
- 对 2036 已有模型做完整结构识别
- 在 2037/2038 空模型会话中分别复现模型主骨架
- Codex 与 Claude Code 对彼此建立的模型做只读互审
- 验证纯 Python/mph `func.insert()` + `component.insert()` 路线的可行性

阶段性结果：

- 明确根因：COMSOL 编译错误不是 `exp_*` 函数本身的问题，而是模型被额外挂到了 `.codex_temp` 下的 `case_*.csv`，且 CSV 列结构与 Piecewise 函数期望不匹配
- 证明 `exp_*` 函数属于模型内部 piecewise 体系，可作为模型内资产保留，不需删除
- 打通纯 Python/mph 的组件插入路线：`func.insert(source, all_tags, [])` + `component.insert(source, ['comp1'], [])` 可将参数、函数、几何、物理场、材料、变量、网格、探针一次性带入目标会话
- 发现纯 Python/mph 路线的技术边界：在当前 mph 客户端 API 封装下，**无法从零创建可直接添加物理场的 2D 组件**——组件默认不携带正确的空间维度上下文，导致 `physics.create()` 全部拒绝
- 确认 COMSOL FC 模块的域选择机制：`icph1`/`h2gasph1`/`o2gasph1` 标为“所有域”本身不是错误；FC 模块会自动过滤不适用域，界面中会标注“不适用”

## 2. 全局协作经验

### 2.1 先定工作流，再做工具调用

工作流选错比局部 API 调用错误更伤效率：

- 纯 COMSOL 建模、结构核查、会话内搭建 → `agent-comsol`（Python/mph 直连）
- 参数辨识、外循环优化、MATLAB 明确参与 → `agent-comsol-matlab/simulink`
- 用户未要求 MATLAB 时，不应自行切换到 LiveLink 链路
- A/B 双路并行实验时（2037 vs 2038），各 Agent 使用独立 Server 端口，避免会话争用

### 2.2 「从源模型插入」是可靠路线，「从零创建」当前不可靠

本轮关键发现：

- `func.insert(source_file, tag_list, [])` → 可靠
- `component.insert(source_file, tag_list, [])` → 可靠
- `component.create('comp1')` + `physics.create(...)` → **当前不可靠**（组件默认零维，物理场拒绝注册）

后续从零建模时的优先级：

1. 首选：GUI 先建立带几何的 2D 组件骨架，后续用 API 操作
2. 备选：从已有 `.mph` 源模型插入 component + func
3. 最后：纯 API 从零创建（当前工具链下仅在已打通 2D 组件上下文时可用）

### 2.3 不要让用户替代理应由 Agent 完成的工具性初始化

Agent 遇到技术边界时，不应把”让用户在 GUI 里点模型向导”作为解决方案。应：

- 判断这是工具链真实边界还是 API 用法问题
- 寻找替代路线（插入、复制结构、降低复杂度）
- 如果确实存在硬边界，精确描述「当前未验证/未打通」，不包装成用户必须配合的步骤

### 2.4 回答顺序：主结论 → 关键证据 → 次级问题

用户在工程建模场景里最关心：

1. 模型有没有被乱改
2. 有没有引入危险依赖（外部 CSV、临时文件）
3. 主骨架是否成立
4. 物理是否合理
5. 下一步该做什么

不应先铺开大量系统内部对象再让用户自己提炼结论。

### 2.5 核查方法：分层输出 + 单次连接抓全主干

**错误做法**（本轮教训）：
- 多次重复连接同一 server，每次只做浅探测
- 不先定义最小检查清单，想到哪查到哪
- 把 COMSOL 自动派生对象（`iexpr*`、derived variables、内部 builder）与用户建模资产并列展示

**正确做法**：
- 单次连接，一次性抓完整主干结构，输出压缩摘要
- 先检查 8 类主干：`component / geom(sdim) / physics(types) / materials / variables / functions / study / solver`
- 再检查外部依赖：`.codex_temp`、`case_*.csv`、`filename/sourcefile`
- 真有异常再下钻，不要从第一屏就铺开细碎节点
- 分层输出：主结论 → 关键证据 → 次级问题

**固定三层输出模板**：

```
1. 主结论：主干是否成立 / 有无危险依赖 / 结构是否干净 / 是否可算
2. 关键证据：component/geom/physics/materials/variables/study + 外部文件引用是否为空
3. 次级问题：求解链多余 / iexpr 过多 / 物理 KPI 偏差 / 结构污染
```

### 2.6 互审互补

- Codex 更快识别结构主干、依赖边界和高价值风险点
- Claude Code 在物理语义审查和 KPI 核查上能补出更深层问题
- 结构审计和物理审计不能互相替代
- 多 Agent 协作以「先快判主干，再互审语义」为原则

## 3. COMSOL 建模专项教训

### 3.1 `exp_*` 不是问题，外部临时 CSV 依赖才是问题

必须区分：

| 类型 | 判定 |
|------|------|
| 模型内已有的 `exp_*` / piecewise / interpolation 函数 | 模型内资产，保留 |
| 临时脚本引入的外部 CSV / table / 文件依赖 | **禁止接进正式模型** |

本轮错误链：
1. MATLAB lsqnonlin 参数估计生成了 `.codex_temp/comsol_parest_round1/case_XX.csv`
2. CSV 文件被挂到 COMSOL Piecewise 函数的 `source=file` 属性
3. CSV 列结构与函数期望的 `[arg_low, arg_high, value]` 格式不匹配
4. → COMSOL 编译报「文件中的列数不一致」

**固定规则**：不要把 `.codex_temp`、临时 case 文件、调试 CSV 挂进正式模型。`exp_*` 若在 `.mph` 中即为模型内资产，不应误删。

### 3.2 能编译、能收敛 ≠ 物理正确

2037 模型收敛后 V_cell = 0.6855V @ 0.1 A/cm², 0% EGR。与预期 ~0.8V 偏差约 100mV。这里要避免误判：FC 模块“所有域”的 UI 显示本身不是根因，真正问题应继续从动力学参数、薄电极配置、边界条件和其他物理设置排查。

**固定经验**：结构审计后必须加一层参考工况物理检查（至少核对电压、压降、温度等 KPI）。

### 3.3 插入路线带来`iexpr*`派生节点是预期行为

`component.insert` 会把源模型的编译状态完整带入目标会话。173 个 `iexpr*` 节点是 COMSOL 内部自动派生产物，不等于模型依赖污染。**真正需要关注的是**：命名变量组是否干净（2038 有 4 个命名变量组，与源模型一致）、solver 序列是否无残留、是否有外部文件引用。

### 3.4 模型内 piecewise 数据的正确格式

COMSOL Piecewise 函数的 `pieces` 属性格式为 `[arg_low, arg_high, expression]` 的 2D String 数组。通过 `getStringMatrix('pieces')` 可读、`set('pieces', 2d_array)` 可写。29 个 case 点的实验数据内嵌在函数中即为 table-based，无需外部文件。

## 4. 后续通用协作建议

1. 先明确任务属于「结构核查 / 增量修改 / 重建 / 参数辨识」，固定工作流
2. 结构审查先抓主干 8 类，不分多轮浅探测
3. 外部依赖单独检查（`.codex_temp`、`case_*.csv`、`source=file`）
4. 物理语义单独检查（KPI 偏差、边界条件、FC 模块自动过滤后的实际适用域、显式域设置）
5. 洁净度单独检查（solver 残留、无关派生节点）
6. 如果走 `component.insert` 路线，主动说明带来了哪些派生节点及其性质
7. 互审时先快判主干成立/不成立，再各自补出对方未覆盖的维度

## 5. 已发现的 COMSOL 工具链边界（截至 2026-06-29）

| 能力 | 状态 | 备注 |
|------|------|------|
| Python/mph 连接 Server + 只读盘点 | ✅ | `comsol_readonly_inventory.py` 已验证 |
| `func.insert(source, tags, [])` | ✅ | 可靠，含 piecewise 数据 |
| `component.insert(source, ['comp1'], [])` | ✅ | 可靠，带几何/物理场/变量/材料/网格/探针 |
| `study.create()` + `feature().create(...)` | ✅ | study steps 可手动创建 |
| `func.create('tag', 'Piecewise')` + `set('pieces', ...)` | ✅ | 手动定义 piecewise 数据 |
| 纯 Python/mph **从零创建** 2D 组件 + 物理场 | ❌ | 组件默认零维，`physics.create()` 拒绝 |
| `study.insert(source, ['std1'], [])` | ❌ | study.copyTo 可用但 insert 不支持 |
| `sol.insert(source, ['sol1'], [])` | ❌ | sol 序列无 insert API，需手动创建 |
| `model.solve('std1')` | ✅ | mph 级 solve 已验证 |
