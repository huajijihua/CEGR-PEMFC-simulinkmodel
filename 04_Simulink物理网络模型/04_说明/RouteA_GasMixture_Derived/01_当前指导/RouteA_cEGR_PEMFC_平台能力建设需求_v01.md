# Route A cEGR-PEMFC 平台能力建设需求

文件类型：规划设计文件  
日期：2026-07-27  
状态：用户确认，新阶段起点  
前置：S2 冷态 smoke 验证通过，S3 稳态验证（恒电流/恒功率/恒电压 + cEGR + 入口组分控制）全部完成

---

## 1. 背景

当前模型已通过 S2 冷态 smoke 验证（4 case 全部通过）和 S3 稳态验证（共 18 个稳态工况 + 6 个组分工况，全部通过）。但现有架构以"可运行的仿真脚本集合"为主，尚未形成"工程师可操作、可扩展的通用仿真平台"。

## 2. 总目标

将当前模型从**科研工作者的个人工具箱**升级为**一个工程师可操作、可扩展的通用仿真平台**。建模围绕三个维度：

| 维度 | 内涵 |
|------|------|
| 结构集成 | 一个 Simulink 模型，派生官方案例，含完整系统拓扑、控制方法、cEGR 技术 |
| 参数匹配 | 参数与结构解耦，参数可独立维护、可追溯来源 |
| 工具化/可视化/扩展化 | 从脚本调用升级为 MATLAB 面板，工程师可操作，可扩展其他结构路线 |

## 3. 核心原则

1. **模型优先**：模型是核心，脚本和面板是辅助，不因工具化牺牲模型质量
2. **鲁棒性 > 极简**：不强制极简脚本，但功能不重复、具备通用性
3. **活动链固定冷启动**：当前 panel/runner 统一使用 cold-start-only；历史初态包只作审计和对比，不进入活动运行链
4. **参数可改**：项目研究无不可改参数（基础物理常数除外）
5. **22 列 profile 必须清理**：趁本次任务彻底收缩为结构体
6. **面板是附加功能**：先把模型和脚本搞好，面板后续再做
7. **模型唯一**：只有一个 `.slx` 文件，派生自官方案例，所有模式在模型内切换

## 4. 文件管理规则

| 规则 | 内容 |
|------|------|
| 唯一模型 | 整个平台只有一个 `.slx`，派生官方案例，含完整系统+cEGR。所有电边界模式、气路控制策略在模型内切换，不复制模型。 |
| 脚本最小化 | 脚本不承担计算功能，仅辅助 Simulink。每个脚本承担某一类通用辅助功能。禁止因多策略/多工况导致脚本数量爆炸。临时脚本使用后立即归档。 |
| 说明文件分类 | 规划设计类（覆盖式更新）和实施记录类（增量式更新）。禁止无限制叠加重复内容。阶段性任务完成后更新所有相关文件。 |

## 5. 平台能力要求

### 5.1 CR1：三种电边界控制

| 模式 | 控制方式 | 实现方式 | 互斥性 |
|------|---------|----------|--------|
| 电流控制 | `I_cmd` 随时间变化 | Simulink 内切换（Variant 或 Mask 参数） | 一次计算只选一种 |
| 功率控制 | `P_cmd` → 内部转换为 `I_cmd` | Simulink 内切换 | 同上 |
| 电压控制 | `V_cmd` → PI 控制器输出 `I_cmd` | Simulink 内切换 | 同上 |

- 允许各电边界各有一个辅助脚本（最多 3 个）
- Simulink 模型本身唯一

### 5.2 CR2：气路控制能力（待详细定义）

控制接口汇总表（待输出），明确区分主动控制量与响应量：

| 类别 | 主动控制量 | 响应量 |
|------|-----------|--------|
| 阴极进气 | 组分、流量/OER、背压、温度、湿度 | 实际流量、压力、温度、组分 |
| cEGR | 目标比/阀开度 | 实际回流比、混合后组分 |
| 阳极进气 | 组分、供氢压力 | 实际流量、压力 |
| 阳极管理 | 回流设置、吹扫设置 | 阳极气体状态 |
| 电堆 | — | 电压、电流、功率、温度 |

**入口气体组分控制要求**：编译时固定值，仿真期间不变。不需动态控制。

### 5.3 CR3：计算前三要素

每次计算前必须明确以下三方面内容（待定义 schema）：

```text
Case 定义：
├── (a) 初始状态：气路和电堆气体状态的初始值（温度、压力、组分、工作点）
├── (b) 控制设置：电边界模式 + 气路命令（引用 CR2 接口表）
└── (c) 求解器设置：Solver、RelTol、AbsTol、MaxStep、StopTime
```

## 6. 阻塞点与抉择点最终结论

### 6.1 无需处理的项目

| 问题 | 结论 |
|------|------|
| 模型独立表达工况（BP1） | 不强制移入模型。移入更好但前提是鲁棒。保持脚本+模型配合，逐步优化。 |
| 官方/自定义组件边界（BP3） | 后续建立组件清单，不阻塞当前工作。 |
| 入口气体组分动态控制（DP1-组分） | 不需要动态控制。编译时固定值，仿真期间不变。 |
| v09 初态 schema（BP5） | v09 及 v10 operating-point bundle 不进入活动 runner；统一执行 cold-start-only，必要时延长研究时长。 |
| 参数分层（DP3） | 可按此结构分层，但项目研究无不可改参数（物理常数除外）。 |
| 扩展性（DP8/DP9） | 当前不讨论，后续再说。 |
| 文件管理（DP10） | 维持当前结构，临时脚本阶段性统一归档。 |

### 6.2 需要执行的任务

| 任务 | 优先级 | 说明 |
|------|--------|------|
| 22 列 profile 收缩为结构体（BP2） | 🔴 高 | 趁本次机会彻底清理，定义最小必要字段的结构体 |
| 控制接口汇总表（DP1） | 🔴 高 | 所有可控制量/可观测量清单，平台操作手册 |
| CR3 三要素 schema（DP2） | 🔴 高 | 标准化每次计算的输入格式 |
| 脚本清理（BP4） | 🟡 中 | 归档临时脚本、合并重复功能 |
| 参数单一入口（BP6） | 🟡 中 | 建立 platform_default_parameters() 函数 |
| 面板设计（BP7/DP4/DP5/BP8） | 🟢 低 | 最后做，先学 App Designer |

## 7. 执行顺序

```
Phase A: 设计基础（纯文档，不涉及模型修改）
├── 第一步：控制接口汇总表
├── 第二步：CR3 三要素 schema 定义
└── 输出：平台能力文档 + 结构体模板

Phase B: 模型优化
├── 第一步：22 列 profile → 结构体（BP2）
├── 第二步：控制逻辑渐进式移入模型（BP1 优化）
└── 第三步：参数单一入口（BP6）

Phase C: 脚本清理
├── 第一步：按接口表审查所有脚本
├── 第二步：归档临时脚本，合并重复功能
└── 第三步：验证核心功能不受影响

Phase D: 工具化（最后做）
├── 第一步：学习 App Designer 官方案例
├── 第二步：设计面板 UI 原型（基础模式 + 高级模式）
├── 第三步：实现面板与 Simulink 接口
├── 第四步：实现结果表格化与可视化
└── 第五步：测试与验证
```
